01 / 企业生产项目

案例：电商「订单 · 支付」微服务平台

假设你在一家中型跨境电商公司做运维。原来所有服务挤在几台物理机上用脚本部署， 每逢大促（如 6·18 / 双 11）流量翻 10 倍，扩容靠人肉、回滚靠运气。 团队决定把核心交易链路微服务化 + 上 Kubernetes，目标是弹性扩缩容、滚动发布零停机、故障自愈。

要上 K8s 的服务（约 8 个微服务 + 中间件）：

API 网关2~6 副本
订单服务3~12 副本
支付服务3~8 副本
库存服务2~6 副本
用户服务2~4 副本
优惠券服务2~4 副本
MySQL / Redis有状态
RabbitMQ有状态
i

为什么这个案例适合讲网络规划？ 支付链路涉及合规与隔离——支付服务不能被随便哪个 Pod 直连， 必须能做网络策略（NetworkPolicy）。这个需求会直接决定后面选哪个 CNI。把业务约束带进网络规划，正是生产和教程 demo 的最大区别。

!

关于「1 个 Master」：本教程为了入门用单 Master，但请记牢—— 单 Master = 控制平面单点故障。Master 挂了，集群无法调度/发布（已运行的 Pod 还在跑）。 真实生产交易系统应是 3 个 Master（堆叠 etcd）+ 负载均衡 VIP。本文会在规划表里标出生产升级路径。

02 / 搭建第一步

规划节点与网络
（动手装机前的全部决策）

K8s 安装失败八成不是装的时候坏，而是规划阶段埋的雷：网段冲突、swap 没关、时间不同步、端口被防火墙挡。 这一步不写一行 K8s 命令，但决定了后面能否一次成功。下面是六项生产级规划清单。

① 角色与硬件规格规划

Master 跑控制平面（apiserver / etcd / scheduler / controller-manager），对磁盘 IO（etcd）和稳定性敏感； Worker 跑业务 Pod，对 CPU / 内存敏感。两类机器规格不该一样。

角色主机名节点 IP规格(入门→生产)说明
Masterk8s-master-0110.10.0.102C4G→4C8G+SSDetcd 强烈建议独立 SSD
Workerk8s-node-0110.10.0.114C8G→8C16G跑订单/支付 Pod
Workerk8s-node-0210.10.0.124C8G→8C16G跑库存/用户 Pod
Workerk8s-node-0310.10.0.134C8G→8C16G中间件 + 弹性
✓

生产细节：节点 IP 用静态地址（绝不能 DHCP 漂移），且四台机在同一二层/可路由网段。 操作系统统一为 Ubuntu 22.04 LTS 或 Rocky Linux 9（不要一台 CentOS 一台 Ubuntu，内核/cgroup 差异会坑你）。

② 三层网络规划（最关键 · 三个网段绝不能重叠）

新手最常见的翻车点：把 Pod 网段、Service 网段，跟公司现有内网（如 10.10.0.0/16）选重了， 导致路由黑洞。K8s 里有三套独立网络，规划时必须互不相交、也不能撞公司现网：

① 节点网络 Node Network
物理机/虚机自己的 IP，由你的机房/云 VPC 决定
② Pod 网络 Pod CIDR
每个 Pod 分到的虚拟 IP，由 CNI 管理（kubeadm 用 --pod-network-cidr 指定）
③ Service 网络 Service CIDR
ClusterIP 虚拟 IP，仅集群内可达，由 kube-proxy 维护
!

本案例特意把 Pod CIDR 设成 172.16.0.0/16， 而不是教程常见的 10.244.0.0/16——因为公司现网是 10.10.0.0/16， 若 Pod 也用 10.x 段就有撞网风险。规划网段先问一句"公司内网用了哪些 10./172./192. 段"，是生产第一性原则。

③ 主机名 / hosts / 时间同步

# 1) 设永久主机名（每台对应改）
hostnamectl set-hostname k8s-master-01

# 2) 四台机统一写 /etc/hosts（保证不依赖外部 DNS 也能互认）
cat >> /etc/hosts <<EOF
10.10.0.10  k8s-master-01
10.10.0.11  k8s-node-01
10.10.0.12  k8s-node-02
10.10.0.13  k8s-node-03
EOF

# 3) 时间必须同步（etcd 对时钟漂移零容忍，差几秒就选主异常）
apt install -y chrony && systemctl enable --now chrony

④ 关 swap + 内核参数（kubelet 的硬性前置条件）

# 关闭 swap：kubelet 默认拒绝在开了 swap 的机器上启动
swapoff -a
sed -i '/ swap / s/^/#/' /etc/fstab   # 永久关闭

# 加载网桥模块 + 打开转发（CNI 流量依赖这些）
modprobe br_netfilter
cat > /etc/sysctl.d/k8s.conf <<EOF
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sysctl --system

⑤ 防火墙端口规划

生产里安全组/防火墙通常默认拒绝。这些端口若没放通，kubeadm init 会卡在"等待控制平面健康"。

节点端口组件方向
Master6443kube-apiserver入 所有节点+运维
Master2379-2380etcd入 仅控制平面
Master10259 / 10257scheduler / cm入 本机
All10250kubelet API入 控制平面
Worker30000-32767NodePort 服务入 按需
All(Calico)179BGP入 节点间

⑥ 容器运行时规划

K8s 1.24 起移除了 Docker 内置支持（dockershim）。生产标准是直接装 containerd， 并把 cgroup 驱动设为 systemd（必须和 kubelet 一致，否则节点 NotReady）。

apt install -y containerd
containerd config default > /etc/containerd/config.toml
# 关键：把 SystemdCgroup 改成 true
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
systemctl restart containerd
✓

第一步交付物（Definition of Done）：一张写满上述信息的《集群规划表》—— 4 行节点清单 + 3 个不冲突网段 + 端口放通确认 + 全节点已关 swap/装好 containerd/时间同步。 只有这张表 100% 填完，才进入第二步 kubeadm init。

04 / 网络组件 CNI

有哪些网络组件？本案例选谁？

K8s 本身不实现 Pod 网络，只定义了 CNI（Container Network Interface）接口标准， 具体由插件实现"让所有 Pod 跨节点互通"。主流选项如下：

Flannel
VXLAN OVERLAY
  • 最简单、装完即用
  • 适合学习/小集群
  • 不支持 NetworkPolicy
  • overlay 有性能损耗
Calico
BGP / IPIP + eBPF
  • 支持 NetworkPolicy（隔离）
  • BGP 模式近原生性能
  • 生产最成熟、社区最大
  • 可平滑升级 eBPF 数据面
Cilium
eBPF NATIVE
  • 性能/可观测性最强
  • L7 策略 + Hubble
  • 学习曲线陡、内核要求高
  • 入门期排障难度大
Canal / Weave
组合 / MESH
  • Canal=Flannel+Calico策略
  • Weave 已停止维护
  • 新项目不推荐
✓

本案例选 Calico，三条决策理由： ①支付链路需要 NetworkPolicy 做服务间隔离（如"只允许网关→订单→支付"的调用链，其它 Pod 禁止直连支付）——Flannel 做不到； ②BGP 模式性能接近裸机，扛得住大促； ③对 4 节点入门集群，Calico 比 Cilium 排障简单、文档丰富、踩坑有人答，是性能与上手难度的最佳平衡点。

Calico 具体怎么搭建（在 kubeadm 集群上）

前置：init 时声明 Pod CIDR

第二步 kubeadm init 时，把规划好的 Pod 网段告诉集群（这就是为什么第一步要先规划网段）：

kubeadm init \
  --pod-network-cidr=172.16.0.0/16 \
  --service-cidr=10.96.0.0/12 \
  --apiserver-advertise-address=10.10.0.10

步骤 1 · 装 Tigera Operator（官方推荐方式）

# Operator 负责管理 Calico 全生命周期，比直接 apply manifest 更易升级
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/tigera-operator.yaml

步骤 2 · 下发 Installation 自定义资源（关键：CIDR 要和 init 一致）

apiVersion: operator.tigera.io/v1
kind: Installation
metadata:
  name: default
spec:
  calicoNetwork:
    ipPools:
    - name: default-pool
      cidr: 172.16.0.0/16     # ← 必须与 --pod-network-cidr 完全一致
      encapsulation: IPIP       # 跨子网用 IPIP；同二层可设 None 走纯 BGP 最快
      natOutgoing: Enabled
      blockSize: 26
kubectl apply -f custom-resources.yaml

步骤 3 · 验证

# 等所有 calico-* Pod 变 Running
kubectl get pods -n calico-system -w

# 节点应从 NotReady 变 Ready（CNI 装好前节点一直是 NotReady）
kubectl get nodes
# NAME            STATUS   ROLES           AGE   VERSION
# k8s-master-01   Ready    control-plane   5m    v1.30.x

# 装 calicoctl 看 IP 池与 BGP 邻居状态
kubectl get ippools -o wide
calicoctl node status   # 看到各节点 BGP 邻居 = Established 即打通

步骤 4 · 兑现案例需求：给支付服务上 NetworkPolicy

这一步正是当初选 Calico 的理由——只允许订单服务访问支付服务，其它 Pod 一律拒绝：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: payment-allow-order-only
  namespace: trade
spec:
  podSelector:
    matchLabels: {app: payment}   # 作用于支付 Pod
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels: {app: order}  # 仅放行订单服务
    ports:
    - {protocol: TCP, port: 8080}
i
