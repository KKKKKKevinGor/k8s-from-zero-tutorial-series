02 / 引导集群

第二步：kubeadm init / join
把四台机拼成一个集群

第一步那张《规划表》在这里全部兑现：规划的 IP、Pod CIDR、Service CIDR、containerd —— 这一步只是把它们"喂"给 kubeadm。 流程分三段：全节点装工具 → Master 初始化 → Worker 加入。

段 A · 三台 + Master 全节点都装 kubeadm/kubelet/kubectl

# 添加 K8s 官方 apt 源（注意 v1.30 这个版本号按需替换）
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.30/deb/Release.key | \
  gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.30/deb/ /' \
  > /etc/apt/sources.list.d/kubernetes.list

apt update && apt install -y kubelet kubeadm kubectl
apt-mark hold kubelet kubeadm kubectl   # 锁版本，防 apt upgrade 把集群升挂
systemctl enable kubelet
!

三大组件别搞混：kubeadm=引导集群的工具（只在装/升级时用）； kubelet=每个节点上的常驻代理（管 Pod 生命周期，全节点都要跑）； kubectl=你敲命令的客户端（其实只需装在你操作的机器上）。

段 B · Master 初始化控制平面

执行 kubeadm init（参数全来自第一步规划）

kubeadm init \
  --apiserver-advertise-address=10.10.0.10 \
  --pod-network-cidr=172.16.0.0/16 \
  --service-cidr=10.96.0.0/12 \
  --control-plane-endpoint=10.10.0.10   # 留好将来扩 3 Master 的入口

成功后屏幕末尾会打印两段关键内容：①配置 kubeconfig 的命令；②给 Worker 用的 kubeadm join 命令（含 token）。把 join 那行复制存好。

配置 kubectl 凭证（否则 kubectl 连不上）

mkdir -p $HOME/.kube
cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
chown $(id -u):$(id -g) $HOME/.kube/config

装 CNI（Part 1 已详解 Calico，这里一行带过）

此刻 kubectl get nodes 看到 Master 是 NotReady —— 正常，因为还没网络插件。装上 Calico 后变 Ready：

kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/tigera-operator.yaml
kubectl apply -f custom-resources.yaml   # cidr: 172.16.0.0/16 见 Part 1

段 C · 三台 Worker 加入集群

在每台 Worker 上执行 Master 打印的那行 join（需 root）：

kubeadm join 10.10.0.10:6443 \
  --token abcdef.0123456789abcdef \
  --discovery-token-ca-cert-hash sha256:1234...ef
✓

token 找不到了 / 过期了（默认 24h）？ 不用重装，在 Master 上一条命令重新生成完整 join 串：

kubeadm token create --print-join-command
# 直接吐出一整行可粘贴的 kubeadm join ... 命令

验证：四个节点全 Ready

kubectl get nodes -o wide
# NAME            STATUS   ROLES           VERSION   INTERNAL-IP
# k8s-master-01   Ready    control-plane   v1.30.x   10.10.0.10
# k8s-node-01     Ready    <none>          v1.30.x   10.10.0.11
# k8s-node-02     Ready    <none>          v1.30.x   10.10.0.12
# k8s-node-03     Ready    <none>          v1.30.x   10.10.0.13

kubeadm 常见报错速查

现象根因解法

i

重来不要怕：任何节点装坏了，kubeadm reset -f 即可清空该节点回到干净状态，再重新 init/join。这是 kubeadm 相比手工二进制部署最大的好处——可重复、可回退。

03 / 部署业务

第三步：部署订单服务
Deployment · Service · Ingress

集群活了，现在把订单服务跑上去。这三个对象各管一件事，缺一不可：

  • Deployment —— 管 Pod 的"多少个副本 + 怎么滚动更新 + 挂了自愈"
  • Service —— 给一组会漂移的 Pod 一个稳定的虚拟 IP/DNS 名，并做负载均衡
  • Ingress —— 七层域名路由，把集群外的 order.shop.com 流量导进来

① Namespace · 先把交易域隔出来

apiVersion: v1
kind: Namespace
metadata:
  name: trade   # 订单/支付/库存都放这个命名空间，便于配额与策略

② Deployment · 订单服务（生产配置，逐项有注释）

apiVersion: apps/v1
kind: Deployment
metadata:
  name: order
  namespace: trade
spec:
  replicas: 3                        # 起步 3 副本，跨节点分布抗单机故障
  selector:
    matchLabels: {app: order}
  strategy:
    type: RollingUpdate          # 滚动发布，零停机
    rollingUpdate: {maxSurge: 1, maxUnavailable: 0}
  template:
    metadata:
      labels: {app: order}   # ← Service 和 NetworkPolicy 靠这个 label 选中
    spec:
      containers:
      - name: order
        image: registry.shop.com/order:v1.4.2  # 用私有仓库+确定 tag，禁用 latest
        ports: [{containerPort: 8080}]
        resources:                       # requests/limits 是调度和稳定性的命脉
          requests: {cpu: 250m, memory: 256Mi}
          limits:   {cpu: 1,    memory: 512Mi}
        readinessProbe:                  # 没就绪不接流量（保护发布期用户）
          httpGet: {path: /healthz, port: 8080}
          initialDelaySeconds: 5
        livenessProbe:                   # 卡死自动重启（自愈）
          httpGet: {path: /healthz, port: 8080}
          initialDelaySeconds: 15
✓

生产细节——三件最容易漏但最致命的： ①resources.requests 决定调度（不写调度器以为 Pod 不耗资源，超卖把节点压垮）； ②readinessProbe 没配，滚动发布时新 Pod 还没启动完就被打流量 → 用户报错； ③镜像用 固定 tag 不用 latest，否则回滚时根本不知道回到哪个版本。

③ Service · 给订单 Pod 一个稳定入口

apiVersion: v1
kind: Service
metadata:
  name: order
  namespace: trade
spec:
  type: ClusterIP        # 集群内访问；对外暴露交给 Ingress，不要滥用 NodePort
  selector:
    app: order          # 选中所有带 app=order 的 Pod 做后端
  ports:
  - {port: 80, targetPort: 8080}

之后支付服务在集群内只需访问 http://order.trade.svc.cluster.local， Pod 怎么扩缩、IP 怎么漂移都跟调用方无关——这就是 Service 解耦的价值。

④ Ingress · 让外网用域名访问

前置：先装一个 Ingress Controller（如 ingress-nginx）

Ingress 只是"路由规则"，真正干活的是 Ingress Controller。先装它：

kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.0/deploy/static/provider/baremetal/deploy.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order
  namespace: trade
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: order.shop.com      # 把这个域名解析到 Ingress 节点
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: order          # 指回上面那个 Service
            port: {number: 80}

⑤ 应用 + 验证

kubectl apply -f trade-ns.yaml -f order-deploy.yaml -f order-svc.yaml -f order-ingress.yaml

kubectl get pods -n trade -o wide   # 3 个 order Pod 分布在不同节点
kubectl get svc,ingress -n trade

# 滚动发布到新版本，看零停机替换
kubectl set image deploy/order order=registry.shop.com/order:v1.4.3 -n trade
kubectl rollout status deploy/order -n trade
kubectl rollout undo   deploy/order -n trade   # 一键回滚到上一个版本

⑥ 大促弹性：HPA 自动扩缩容

呼应案例最初的诉求——大促流量翻 10 倍。配 HPA，让订单服务按 CPU 自动从 3 副本扩到 12：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: order, namespace: trade}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: order}
  minReplicas: 3
  maxReplicas: 12
  metrics:
  - type: Resource
    resource: {name: cpu, target: {type: Utilization, averageUtilization: 70}}
!

HPA 依赖 Metrics Server：得先装 metrics-server，否则 HPA 拿不到 CPU 指标， kubectl get hpa 的 TARGETS 列会一直显示 <unknown>。 另外 HPA 是按 requests 算利用率的——这又回到第③步"必须写 resources.requests"。
