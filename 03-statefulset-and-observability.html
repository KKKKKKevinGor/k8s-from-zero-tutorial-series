04-A / 有状态服务

MySQL / Redis 怎么上 K8s？
StatefulSet + 持久化存储

前两篇里订单/支付是无状态的——Pod 挂了重建一个一模一样的就行。但 MySQL、Redis、RabbitMQ 是有状态的： 它们有身份（谁是主、谁是从）和数据（不能随 Pod 销毁而丢）。这就需要两个新对象：

  • StatefulSet —— 给 Pod 稳定的名字（mysql-0、mysql-1）和稳定的网络标识，按序启停
  • PV / PVC / StorageClass —— 把数据存到 Pod 生命周期之外的持久卷，Pod 重建数据还在

存储三件套的关系（先理解再写 YAML）

① 准备 StorageClass（裸机集群常用 local-path / Ceph / NFS）

云上直接用厂商 CSI（如 EBS）；裸机入门最省事是 Rancher 的 local-path-provisioner：

kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/v0.0.30/deploy/local-path-storage.yaml
kubectl get storageclass   # 看到 local-path 即可
!

local-path 仅供入门/测试：它把数据存在Pod 所在节点的本地盘，节点挂了数据就没了，且 Pod 被绑死在该节点。 生产 MySQL 必须用网络存储（Ceph RBD / 云盘 CSI），才能保证节点故障时数据不丢、Pod 能漂到别的节点拉起。

② StatefulSet 部署 MySQL（关键在 volumeClaimTemplates）

apiVersion: apps/v1
kind: StatefulSet
metadata: {name: mysql, namespace: trade}
spec:
  serviceName: mysql          # 必须配套一个 Headless Service 给稳定 DNS
  replicas: 1
  selector: {matchLabels: {app: mysql}}
  template:
    metadata: {labels: {app: mysql}}
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        env: [{name: MYSQL_ROOT_PASSWORD, valueFrom: {secretKeyRef: {name: mysql-secret, key: pwd}}}]
        ports: [{containerPort: 3306}]
        volumeMounts: [{name: data, mountPath: /var/lib/mysql}]
  volumeClaimTemplates:           # ← StatefulSet 独有：给每个 Pod 自动建专属 PVC
  - metadata: {name: data}
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: local-path
      resources: {requests: {storage: 20Gi}}
✓

密码别写明文——用 Secret：kubectl create secret generic mysql-secret -n trade --from-literal=pwd='强密码'。 上面 env 用 secretKeyRef 引用它，YAML 里就不会出现真实密码（也别提交进 Git）。

i

什么时候别自己写 StatefulSet？ 生产做 MySQL/Redis 高可用（主从、故障自动切换、备份）非常复杂。 更稳的做法是用 Operator（如 mysql-operator、redis-operator）—— 它把"建主从、选主、备份"的运维知识固化成代码，你只写一个简单的 CR 即可。入门理解 StatefulSet，生产用 Operator。

04-B / 可观测性

线上出事怎么第一时间知道？
监控 · 日志 · 追踪三支柱

无监控的集群 = 蒙眼开车。可观测性（Observability）有三大支柱，回答三类不同的问题：

METRICS · 指标
Prometheus
"系统现在健康吗？" CPU/内存/QPS/错误率，可告警
+ Grafana 可视化
LOGS · 日志
Loki
"那一刻具体发生了什么？" 逐行日志，事后定位
+ Promtail 采集
TRACES · 链路
Tempo / Jaeger
"慢在哪个服务？" 一次请求穿过多个微服务的耗时
进阶 · 本篇略

前置：用 Helm 装（生产标准方式）

监控栈组件多、配置杂，手写几十个 YAML 不现实。Helm 是 K8s 的包管理器（类比 apt/npm），一条命令装一整套：

# 装 Helm
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

① 监控：kube-prometheus-stack（Prometheus + Grafana + Alertmanager 一包搞定）

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install kps prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace

装完即自带：节点/Pod/集群组件的全套指标采集 + 几十个开箱 Grafana 仪表盘。访问 Grafana：

# 取 Grafana admin 密码
kubectl get secret -n monitoring kps-grafana -o jsonpath="{.data.admin-password}" | base64 -d
# 本地端口转发先看效果（生产再用 Ingress 暴露）
kubectl port-forward -n monitoring svc/kps-grafana 3000:80

让 Prometheus 抓订单服务的自定义指标（ServiceMonitor）

这是闭环关键——把 Part 2 部署的订单服务接入监控。前提是订单服务暴露了 /metrics 端点：

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: order
  namespace: monitoring
  labels: {release: kps}   # 必须带这个 label，Prometheus 才会发现它
spec:
  namespaceSelector: {matchNames: [trade]}
  selector: {matchLabels: {app: order}}   # 选中订单 Service
  endpoints: [{port: http, path: /metrics, interval: 15s}]

② 告警：订单错误率超阈值就通知（PrometheusRule）

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata: {name: order-alerts, namespace: monitoring, labels: {release: kps}}
spec:
  groups:
  - name: order.rules
    rules:
    - alert: OrderHighErrorRate
      expr: sum(rate(http_requests_total{app="order",code=~"5.."}[5m]))
            / sum(rate(http_requests_total{app="order"}[5m])) > 0.05
      for: 3m                  # 持续 3 分钟才告警，避免抖动误报
      labels: {severity: critical}
      annotations: {summary: "订单 5xx 错误率 >5% 已持续 3 分钟"}
✓

告警接到哪？ Alertmanager（已随 stack 装好）负责路由——配上钉钉/企业微信/Slack webhook， 上面这条规则触发时就会自动推送到值班群。for: 3m 这种"持续时间窗"是生产告警防骚扰的核心技巧。

③ 日志：Loki + Promtail（轻量、与 Grafana 同源）

为什么不用经典的 EFK（Elasticsearch）？Loki 只索引标签不索引全文，资源占用小得多， 且直接复用上面那套 Grafana 界面——对中小集群是性价比最高的选择。

helm repo add grafana https://grafana.github.io/helm-charts
helm install loki grafana/loki-stack \
  -n monitoring --set promtail.enabled=true

Promtail 以 DaemonSet 形式在每个节点跑一份，自动收集所有 Pod 的 stdout 日志推给 Loki。 然后在 Grafana 加 Loki 数据源，就能用 {app="order"} |= "error" 这样查日志：

i

DaemonSet 是第四种工作负载：前面见过 Deployment（无状态）、StatefulSet（有状态）、 这里的 DaemonSet 保证"每个节点恰好跑一个 Pod"——日志采集、网络插件、监控 agent 都用它。 加上跑一次性任务的 Job/CronJob，K8s 五种核心工作负载就齐了。
